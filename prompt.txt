You are the lead performance engineer for the "elaina-cpp" project.

Repository:
https://github.com/H2O-Xrp/elaina-cpp

Your objective is to evolve Elaina C++ into an extremely high-performance HTTP framework whose real-world throughput, latency, scalability, and memory efficiency are competitive with or exceed ElysiaJS running on Bun.

IMPORTANT:
Do NOT blindly rewrite the project.
Do NOT optimize based on intuition alone.
Do NOT sacrifice correctness for benchmark numbers.
Do NOT introduce unnecessary dependencies.
Do NOT replace the existing architecture unless profiling and benchmark evidence shows that the architecture itself is the bottleneck.

The project is C++20 and Linux-first. Preserve the existing public API where practical.

3. ZERO-COPY / ZERO-ALLOCATION HOT PATH

Aggressively minimize allocations inside the request hot path.

The ideal request path should approach:

socket
-> event notification
-> parse request
-> route
-> invoke handler
-> construct response
-> write response

without heap allocation whenever possible.

Investigate:

- "std::string"
- "std::vector"
- "std::function"
- "std::shared_ptr"
- "std::unique_ptr"
- exceptions
- temporary objects
- temporary strings
- dynamic polymorphism
- virtual calls
- copying headers
- copying route parameters
- copying request bodies

Prefer:

- "std::string_view"
- "std::span"
- fixed-capacity containers
- intrusive structures where appropriate
- arena/request-local allocation
- object pools
- reusable buffers
- stack storage
- compile-time structures
- move semantics
- small-buffer optimization

Do NOT blindly replace everything with custom allocators.

Benchmark every allocator-related change.

==================================================
4. HTTP PARSER

Optimize "StrictHttpParser".

Goals:

- zero allocation
- zero unnecessary copying
- predictable branches
- sequential memory access
- efficient CRLF detection
- efficient header parsing
- efficient method parsing
- efficient HTTP version parsing

Investigate SIMD where beneficial.

Consider:

- SSE4.2
- AVX2
- ARM NEON

But provide portable fallback implementations.

Do not introduce SIMD merely because it looks impressive.

Benchmark:

- tiny requests
- many headers
- large headers
- query strings
- POST bodies
- malformed requests

Ensure parser correctness and security.

Fuzz the parser.

The router must be extremely fast.

Current architecture uses a segment trie.

Benchmark and optimize:

dynamic parameters
wildcards

route misses

Investigate:

- radix tree
- compressed trie
- flat route tables
- hash-based static route lookup
- perfect hashing

- contiguous memory layouts

Use a hybrid strategy if it wins:

O(1) / hash-based lookup

dynamic routes:

wildcards:
specialized fallback

Do NOT assume one data structure is optimal for every route type.

Benchmark route tables containing:

10 routes
100 routes

10,000 routes
100,000 routes

Measure both hit and miss performance.

9. RESPONSE PATH

Optimize response generation.

For static responses:

Prefer precomputed response metadata.

For example:

HTTP/1.1 200 OK
Content-Type: text/plain
Content-Length: ...

should not be reconstructed from scratch on every request when avoidable.

Investigate:

- static response caching
- response templates
- scatter/gather writes
- "writev"
- "sendmsg"
- buffer reuse

For very small responses, benchmark direct writes versus buffered responses.

Avoid converting:

string -> temporary string -> buffer -> socket

when a direct path is possible.

==================================================
10. HEADER REPRESENTATION

Design headers for speed.

Avoid:

map<string,string>

in the hot path.

Investigate:

- compact arrays
- string_view
- static header IDs
- enum-based known headers
- hash lookup for known headers
- contiguous storage

Known headers should ideally avoid expensive string hashing.

==================================================
11. CONTEXT OBJECT

Optimize "Context".

A handler such as:

app.get("/users/:id", [](Context& ctx) {
return Response::text(ctx.param("id"));
});

should have extremely low overhead.

"ctx.param()", "ctx.query()", "ctx.header()", etc. should avoid:

- allocations
- locks
- string copies
- dynamic dispatch

Prefer views into the original request buffer when lifetime permits.

Clearly document lifetime guarantees.

==================================================

Response::status(200)

Response::body(...)

Common static responses should have specialized fast paths.

Avoid abstraction overhead.

Use compile-time specialization when beneficial.
